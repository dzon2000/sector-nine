**Status:** implementation complete, final CI gate to verify

**Scope:** deterministic engine event counters, bounded save representation, inspector, mission throughput HUD, Playwright display verification.

## Engine event semantics

All diagnostic observations come from the same fixed-step deterministic engine as material transport and operating costs. They are not derived from canvas pixels, animation, browser wall-clock time or merely occupied tiles.

1. **Sampling boundary:** one sample is written after production completion, physical transfer arbitration, and cycle start decisions, during each unpaused engine tick.
2. **Machine status:** for each producer/processor, exactly one status per observed tick: `working` (cycle active or mine ready for work), `input_starved` (processor lacks a complete recipe and has no cycle/output), or `output_blocked` (machine still holds a produced output after transfer attempts). Machine statuses are mutually exclusive.
3. **Completed units:** count an actual output produced when a mine finishes its cycle or a processor finishes its recipe. This is distinct from later terminal sales or time spent working.
4. **Conveyor moves:** count a real approved departure from that conveyor in the transfer phase, not an arrival to it.
5. **Conveyor stalls:** count a conveyor that actually held material at the pre-transfer boundary and did **not** obtain approval for departure. An occupied belt transferring to the next occupied but simultaneously vacated belt is **not** stalled.
6. **Terminal intake:** count actual accepted sales per material, as determined by physical successful transfers to the permanent terminal, independent of item production counters.

## Bounded data and percentages

The persistent `diagnostics.samples` history contains at most 60 consecutive **active** simulation ticks, each storing entity-ID-keyed observations and terminal sales per item. The existing mission-local sales history remains independent; completing or activating a new mission does not reset terminal diagnostics.

Inspector rates are calculated from samples actually observed since placement or the newest diagnostic epoch:
- `Processing % = workingTicks / observedTicks × 100`.
- `Input-starved % = inputStarvedTicks / observedTicks × 100`.
- `Output-blocked % = outputBlockedTicks / observedTicks × 100`.
- `Completed units per 60 = completedUnits / observedTicks × 60`; the UI also shows the observed tick count so partial windows are not mistaken for complete measurements.

Stable entity IDs prevent data from being attributed to a new structure at a demolished structure's former location. Demolition prunes old entity entries from recent history. Newly placed structures start with no statistics, and then accumulate only their own active-tick samples.

The save validator initializes `diagnostics: {samples: []}` for older valid snapshots lacking the field and rejects malformed, non-consecutive, oversized, negative or stale samples. Existing schema v3, v2 and v1 migration and legacy mission rules remain intact.

## UI behavior

- **Selected structure inspector:** working/processing share, missing-input share, output-blocked share, completed production and per-60 rate, or conveyor successful movements and blocked dwell, plus actionable, material-specific input/output/route hint.
- **Terminal section:** observed ticks and actual sales counts for iron ore, iron ingots, coal, gears and steel. No automatic assertion that the terminal is congested.
- **M6/M7 mission HUD:** actual mission-local 60-tick gear/steel sales, current operating profit where applicable, Advanced Smelting status, saved stability streak and the first unmet condition. Before 60 valid mission-local ticks it explicitly reports a collecting window.
- **Legacy M6/M7:** retain prior cumulative mission progress display and are not shown the v3 stability objective.
- Sections use semantic headings, text labels and accessible section names, rather than color-only signals or forced modal interruptions. Existing keyboard construction and inspector controls remain unchanged.

The detailed M6/M7 story text and tutorial remain WP5 responsibilities; WP4 focuses on accurate operational status and player-facing progress.

## Boundary and exclusions

Counters do not change recipes, costs, tick order, transfers, arbiter choice, construction rules or any mission thresholds. No offline progression, storage, telemetry service, wall-clock production or new gameplay buildings were added.

**Acceptance mapping:** V03-AC-11, V03-AC-12, and persistence/transport portions of V03-AC-16. Human optimization playtest evidence remains a later work package.
