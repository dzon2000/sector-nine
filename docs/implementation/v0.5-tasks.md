## Dependency order and gates

**WP0 planning approval → WP1 → WP2 → WP0 final freeze → WP3 → WP4 → WP5 → WP6.**

WP0 is a two-stage design gate, not a claim that unknown thresholds are approved. WP1 is independently useful. WP2 may create headless experimental fixtures/probes after approval; it must not silently ship unapproved missions or tune production constants. Each package ends with independent QA evidence and Product Owner review before progression. Functional work uses RED → GREEN → refactor.

## WP1 — Remove legacy-save compatibility

Scope: runtime cleanup required by ADR-0006, independent of new missions. AC-01/03/04 and the M1–M10 portion of AC-02. Chapter III restore remains NOT RUN until WP3; do not mark all of AC-02 complete in WP1.

1. Inventory compatibility code and tests in persistence, domain initialization, mission evaluators and chapter transitions. Distinguish migrations from ordinary current-campaign progression and useful validation.
2. RED: current-format roundtrips from M1, M6/M7, M10 and free play; active reservations/fuel/arbiters/windows; invalid/unsupported snapshots; no silent overwrite; explicit restart.
3. Create one current-version schema from new-game initialization. Decouple chapter/rule identities from legacy save versions, retaining provenance needed for current gameplay and reports.
4. Delete v1→v2→v3→v4 conversion paths, legacy-only grandfathering and old cumulative M6/M7 evaluators. Replace useful old fixtures with current initializers. Do not delete current mechanic/economic assertions because their files mention older releases.
5. Keep raw unsupported/corrupt data untouched until explicit restart. Prevent autosave/queued writes from clobbering rejected data or the newly reset game. No historical archive UI or migration framework.
6. Deliver the minimal complete unsupported/corrupt-save UI now: actionable explanation, explicit restart confirmation, and cancel without mutation. Update save messages and release notes: older saves require a fresh start; current-version reload is supported. Verify a full current M1–M10 campaign and browser restart/restore flow. This safety behavior must not wait for WP4.

Exit: no runtime dependency on historical migration for fresh campaigns; deterministic restore and existing gameplay regressions pass. Record removed branches/tests and replacement coverage. No archived human-save migration gate.

## WP2 — Headless contract feasibility and recovery

Entry: accepted bounded design direction and WP1. AC-04/05/07.

- Derive candidate goals from actual resource, terminal and power ceilings. Use existing M10 paid-campaign factory as a starting point and test whether it already satisfies candidate objectives without new decisions.
- Prototype M11–M13 objective observations in test-only probes; compare both M12 routes with traceable physical production/sales, peak and sustained throughput, profit, capital spent, rebuild count and active ticks.
- Reach each route from a genuine engine-generated 300-Cr fresh campaign using paid commands. Label engine saves as synthetic, not human evidence. No injected inventory/credits in economic feasibility proofs.
- Include one recoverable construction/routing mistake and show continued revenue/recovery for each route. Report time spent financing separately from fixed mission windows.
- Negative cases: stockpiled goods, pre-activation history, low-capacity/underpowered factory, no-demand power, partial windows, paused/offline time and reload near completion.
- Publish candidate thresholds, layouts, ledger audits and alternatives. Stop for design review if board capacity, repetitive rebuilds or idle waiting dominate. Do not expand the board or introduce new machines to rescue a candidate.

Exit: feasible, distinct profiles and evidence returned to WP0 final freeze. Automated run duration is not human decision time or proof of enjoyment.

## WP5 — Story and playtest evidence

Entry: WP4. AC-10/11.

- Extend local opt-in recorder with contract transitions/choice identity and honest build/schema/rule provenance. Preserve planning, credit waiting, mission waiting, paused and unclassified categories.

## WP6 — Integrated QA, human acceptance and release preparation

Entry: WP1–WP5 accepted. AC-01–13.

- Full Vitest, TypeScript/Vite build and Playwright suite; final commit/CI provenance; fresh M1–M13 campaigns for both routes and current-version deterministic restore at critical boundaries.
- Review diff for residual legacy requirements/code, accidental economy changes, stale UI regressions, reward duplication and new softlocks. AC matrix must distinguish PASS, FAIL, BLOCKED and NOT RUN.
- Owner plays Chapter III with real decisions and rebuilds, evaluates both route previews/consequences, tests current-version restore and explicit restart, and supplies qualitative feedback/recorder evidence. A second full route can be a focused human follow-up; automated coverage of both is mandatory.
- Record active ticks versus actual human planning/credit/mission waiting, clarity and repetition. No fabricated timings and no genuine legacy-save requirement.
- Prepare acceptance report, release checklist and PR to develop; resolve review findings. Merge/tag/publish/issue closure require separate explicit authorization.

Exit: full evidence plus human acceptance; release actions remain gated.
